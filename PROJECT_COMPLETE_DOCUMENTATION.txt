1. PROJECT OVERVIEW & METADATA
================================================================================

1.1 Project Title:
Event Registration Management System (Academic Database Systems Project)

1.2 Primary Objective:
To design, implement, and demonstrate a database-driven web application for managing
college event registrations. The central pedagogical goal of this project is to prove
genuine, server-side execution of MongoDB search, comparison, logical, and sorting
queries directly within the database management system (via Mongoose ODM) rather than
relying on in-memory JavaScript array manipulation.

1.3 Problem Statement:
In academic institutions, extracurricular and academic events (technical symposiums,
cultural fests, sports tournaments, workshops, and seminars) involve managing participant
registrations across multiple categories, variable registration fee structures, and distinct
payment states. Traditional registration workflows suffer from critical vulnerabilities:
  - Manual paper forms and standalone spreadsheets (Excel, Google Sheets) lack atomic
    concurrency control, resulting in duplicate entries, data loss, and formatting errors.
  - Basic spreadsheet filters cannot handle composite multi-criteria queries efficiently
    (e.g., finding participants in "Workshop" whose payment is "Pending" and fee is >= 300).
  - Common student web projects frequently fetch entire collections into the web browser
    and execute filtering via client-side JavaScript (`Array.prototype.filter()`,
    `Array.prototype.sort()`). This anti-pattern defeats the purpose of learning database
    management systems, wastes network bandwidth, and does not scale.

1.4 Scope & Boundaries:
  - Scope: Management of participant registration records, collection-level query execution,
    real-time multi-operator filtering, systematic sequential identification (EM101, EM102...),
    single-page dashboard management, full CRUD operations, and responsive web presentation.
  - Boundaries: Single-organization scope without multi-tenant authentication; focuses on
    administrative registration management rather than payment gateway integrations.

1.5 Target Users:
College event administrators, department coordinators, student activity conveners, and
faculty event evaluators.

1.6 Core Differentiator:
Every filter, search input, fee range, category checkbox, and sorting dropdown triggers an
asynchronous HTTP request that causes the Express backend to build a native MongoDB query
tree (`$and`, `$or`, `$in`, `$gt`, `$lt`, `$gte`, `$lte`, `$ne`, `.sort()`). The database
executes the query and returns only the matching records.

4.3 Indexes in MongoDB:
Verified directly from the live database engine using `db.collection('registrations').indexes()`:

  1. `_id_`: Default unique B-tree index on `_id: 1`
  2. `registrationId_1`: Unique B-tree index on `registrationId: 1`
     - Purpose: Guarantees uniqueness for systematic identifiers and provides O(1) lookup times.
  3. `participantName_text_eventName_text`: Compound Text Index
     - Purpose: Accelerates full-text searching across participant names and event names.
  4. `eventCategory_1`: Single-field index on `eventCategory: 1`
     - Purpose: Accelerates exact and `$in` categorical filtering.
  5. `paymentStatus_1`: Single-field index on `paymentStatus: 1`
     - Purpose: Optimizes payment state queries and `$ne` exclusion operations.
  6. `registrationDate_1`: Single-field index on `registrationDate: 1`
     - Purpose: Accelerates chronological sorting and date range queries (`$gte`, `$lte`).
  7. `fee_1`: Single-field index on `fee: 1`
     - Purpose: Accelerates numerical range comparisons (`$gt`, `$lt`, `$gte`, `$lte`).

4.5 Design Rationale:
  - Single Collection Structure: In this college event system, each registration document
    encapsulates the complete transaction (participant identity, event classification, financial
    fee, payment state, and date). Denormalizing event details into the registration document
    eliminates expensive `$lookup` joins, optimizing the collection for high-throughput reads
    and multi-parameter filtering.
  - Systematic vs Object Identifier: MongoDB's default 24-character hex `_id` is retained as
    the immutable primary key, while a business-level `registrationId` (`EM101`) is introduced
    for human readability, communication, and systematic sorting.

5. COMPLETE CRUD IMPLEMENTATION LIFECYCLE
================================================================================

The application implements complete Create, Read, Update, and Delete operations.

5.1 CREATE Operation:
  - Client Flow:
    1. User fills the form or clicks "Fill Sample" to populate test data.
    2. Client validation checks all fields (`validateForm()`).
    3. `app.js` makes an asynchronous `POST` request to `/api/registrations` with JSON payload.
  - Server Flow:
    1. Express receives `req.body` and extracts whitelisted fields.
    2. Auto-increment logic executes:
       ```javascript
       const all = await Registration.find(
         { registrationId: { $regex: /^EM\d+$/i } },
         { registrationId: 1 }
       );
       let maxNum = 100;
       for (const doc of all) {
         if (doc.registrationId) {
           const n = parseInt(doc.registrationId.replace(/^EM/i, ''), 10);
           if (!isNaN(n) && n > maxNum) maxNum = n;
         }
       }
       registrationData.registrationId = `EM${maxNum + 1}`;
       ```
    3. An instance of `Registration` is instantiated: `const registration = new Registration(registrationData);`
    4. Mongoose executes validation rules and writes the document to MongoDB via `await registration.save();`
    5. Returns HTTP 201 Created with `{ success: true, message: '...', data: saved }`.
  - Frontend Response:
    A success toast notification appears, form resets, and `loadRegistrations()` reloads the table.

5.2 READ Operations:
  - Read All (with Filters & Sorting):
    - Client: `loadRegistrations()` builds query string parameters and calls `GET /api/registrations?<params>`.
    - Server: `buildQuery(req.query)` builds the MongoDB query object. Sort object is validated.
    - MongoDB Execution: `const registrations = await Registration.find(query).sort(sortObj);`
    - Response: HTTP 200 with `{ success: true, count: ..., query: query, data: registrations }`.
    - Client: Renders table rows, result count badge, active filter pills, and active MongoDB query.
  - Read Single Document:
    - Client: User clicks "View" on any table row, passing the document `_id`.
    - Server: Executes `GET /api/registrations/:id`.
    - MongoDB Execution: `const registration = await Registration.findOne({ _id: req.params.id });`
    - Response: HTTP 200 with full document metadata.
    - Client: Injects metadata into `#modal-content` and opens `#detail-modal`.

5.3 UPDATE Operation:
  - Client Flow:
    1. User clicks "Edit" button in table row or view modal.
    2. Client fetches document data and populates form inputs.
    3. Form title switches to "Edit Registration", submit button changes to "Update Registration",
       and "Cancel" button appears.
    4. User alters fields (e.g., updates fee or changes status from Pending to Paid).
    5. Client sends `PUT /api/registrations/:id` with updated payload.
  - Server Flow:
    1. Verifies document exists: `await Registration.findOne({ _id: req.params.id });`
    2. Whitelists permitted fields into `updateData`.
    3. Executes atomic update on MongoDB:
       ```javascript
       await Registration.updateOne(
         { _id: req.params.id },
         { $set: updateData },
         { runValidators: true }
       );
       ```
    4. Fetches updated document: `await Registration.findOne({ _id: req.params.id });`
    5. Returns HTTP 200 with updated document.
  - Frontend Response:
    Displays success toast, resets form to Add mode, and refreshes table.

5.4 DELETE Operation:
  - Client Flow:
    1. User clicks "Delete" on a table row.
    2. Confirmation modal displays: "Are you sure you want to delete the registration for [Name]? This action cannot be undone."
    3. User clicks "Delete" button inside modal.
    4. Client sends `DELETE /api/registrations/:id`.
  - Server Flow:
    1. Verifies document exists: `const existing = await Registration.findOne({ _id: req.params.id });`
    2. Executes removal in MongoDB: `await Registration.deleteOne({ _id: req.params.id });`
    3. Returns HTTP 200: `{ success: true, message: 'Registration for "[Name]" deleted successfully' }`.
  - Frontend Response:
    Hides modal, displays success toast, and re-executes `loadRegistrations()`.

5.5 AGGREGATION Pipeline (Summary Statistics):
  - Endpoint: `GET /api/registrations/stats/summary`
  - MongoDB Execution:
    ```javascript

      {
        $group: {
    ```

6. MONGODB QUERY ENGINE & OPERATOR SPECIFICATIONS
================================================================================

This section details how the backend `buildQuery()` function in `routes/registrations.js`
constructs native MongoDB query objects.

6.1 Verification of Server-Side Execution:
The frontend JavaScript (`app.js`) NEVER calls `Array.prototype.filter()`, `Array.prototype.find()`,
or `Array.prototype.sort()` to process database records. It transmits parameters to Express,
Express builds the query object, and Mongoose invokes MongoDB's C++ database engine.

6.2 Search Operations:
  1. Search by Registration ID:
     - Parameter: `searchById=EM105`
     - Backend Implementation:
       ```javascript
       const rawId = searchById.trim();
       const escaped = rawId.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
       andClauses.push({ registrationId: { $regex: new RegExp(escaped, 'i') } });
       ```
     - Result: Matches exact systematic ID case-insensitively (e.g. `EM105` or `em105`).
  2. Search by Participant Name:
     - Parameter: `search=Aarav`
     - Backend Implementation:
       ```javascript
       const regex = new RegExp(search.trim().replace(/[.*+?^${}()|[\]\\]/g, '\\$&'), 'i');
       andClauses.push({ participantName: { $regex: regex } });
       ```
     - Result: Matches any participant whose name contains the substring.

6.3 Comparison Operators:

  1. Operator `$gt` (Greater Than):
     - Parameter: `feeGt=500`
     - Constructed MongoDB Query: `{ fee: { $gt: 500 } }`
     - Purpose: Finds registrations where `fee` is strictly greater than 500.
     - Actual Seed Result: Matches `EM101` (₹1500), `EM106` (₹750), `EM108` (₹800), `EM111` (₹1200), `EM115` (₹950).

  2. Operator `$lt` (Less Than):
     - Parameter: `feeLt=300`
     - Constructed MongoDB Query: `{ fee: { $lt: 300 } }`
     - Purpose: Finds registrations where `fee` is strictly below 300.
     - Actual Seed Result: Matches `EM103` (₹200), `EM105` (₹150), `EM107` (₹100), `EM109` (₹250), `EM110` (₹100), `EM112` (₹50), `EM113` (₹0), `EM114` (₹200), `EM116` (₹75).

  3. Operator `$gte` (Greater Than or Equal):
     - Parameters: `feeGte=200` or `dateFrom=2026-03-01`
     - Constructed MongoDB Query: `{ fee: { $gte: 200 } }` or `{ registrationDate: { $gte: ISODate(...) } }`
     - Purpose: Finds records with values greater than or equal to the threshold.

  4. Operator `$lte` (Less Than or Equal):
     - Parameters: `feeLte=800` or `dateTo=2026-05-31`
     - Constructed MongoDB Query: `{ fee: { $lte: 800 } }` or `{ registrationDate: { $lte: ISODate(...) } }`
     - Purpose: Finds records with values less than or equal to the threshold. When used on dates,
       the backend adjusts `dateTo` to 23:59:59.999 of that day to encompass the full date.

  5. Operator `$ne` (Not Equal):
     - Parameter: `paymentNe=Paid` or `feeNe=500`
     - Constructed MongoDB Query: `{ paymentStatus: { $ne: 'Paid' } }` or `{ fee: { $ne: 500 } }`
     - Purpose: Excludes documents matching the specified value. For example, `{ paymentStatus: { $ne: 'Paid' } }`
       retrieves all registrations that are `Pending` or `Failed`.

6.4 Logical Operators:

  1. Operator `$and` (Logical Conjunction):
     - Trigger: Any scenario where two or more query conditions are supplied simultaneously.
     - Construction Logic:
       Individual condition objects are pushed into an array `andClauses`.
       ```javascript
       if (andClauses.length === 0) return {};
       if (andClauses.length === 1) return andClauses[0];
       return { $and: andClauses };
       ```
     - Example Query:
       ```javascript
       {
         "$and": [
           { "eventCategory": "Workshop" },
           { "paymentStatus": "Paid" },
           { "fee": { "$gt": 400 } }
         ]
       }
       ```
     - Actual Seed Result: Matches `EM102` (Web Dev Bootcamp, ₹500), `EM111` (Data Science Bootcamp, ₹1200),
       and `EM115` (Cloud Computing 101, ₹950).

  2. Operator `$or` (Logical Disjunction):
     - Parameter: `orSearch=Cricket`
     - Constructed MongoDB Query:
       ```javascript
       {
         "$or": [
           { "participantName": { "$regex": /Cricket/i } },
           { "eventName": { "$regex": /Cricket/i } }
         ]
       }
       ```
     - Purpose: Evaluates to true if EITHER participant name OR event name matches the expression.
     - Actual Seed Result: Matches `EM104: Rohan Mehta - Cricket League 2026`.

  3. Operator `$in` (Set Membership):
     - Parameters: Multi-category selection `eventCategory=Technical,Workshop` or multi-status `paymentStatus=Paid,Pending`
     - Construction Logic:
       ```javascript
       const categories = eventCategory.split(',').map(c => c.trim()).filter(c => ALLOWED_CATEGORIES.includes(c));
       if (categories.length > 1) {
         andClauses.push({ eventCategory: { $in: categories } });
       }
       ```
     - Constructed MongoDB Query:
       ```javascript
       {
         "eventCategory": {
           "$in": ["Technical", "Workshop"]
         }
       }
       ```
     - Purpose: Matches documents whose category equals ANY of the elements in the specified array.
     - Actual Seed Result: Matches `EM101`, `EM102`, `EM106`, `EM108`, `EM111`, `EM115`.

6.5 Sorting Engine:
  - Parameters: `sortBy=fee`, `sortOrder=desc`
  - Backend Whitelist Check:
    Allowed sort fields: `['registrationId', 'participantName', 'registrationDate', 'fee', 'eventName', 'createdAt']`
    Allowed sort orders: `['asc', 'desc']`
  - MongoDB Construction:
    ```javascript
    const sortObj = { [sortField]: sortOrder === 'asc' ? 1 : -1 };
    Registration.find(query).sort(sortObj);
    ```
  - Result: Sorts the cursor directly within MongoDB before returning results to Express.

8.1 Endpoint: GET /api/registrations
  - Purpose: Retrieve all registrations or query matching registrations.
  - Query Parameters (All optional):

10. VALIDATION, SECURITY & ERROR-HANDLING MATRIX
================================================================================

10.1 Multi-Layer Validation Strategy:
  - Layer 1 (Client-Side Pre-Flight):
    `validateForm()` inspects field values prior to network calls, setting visual error classes
    (`input.invalid`) and injecting inline text warnings (`#err-[field]`).
  - Layer 2 (Backend Whitelist Filtering):
    In `routes/registrations.js`, untrusted user input is explicitly checked against strict
    arrays (`ALLOWED_SORT_FIELDS`, `ALLOWED_SORT_ORDERS`, `ALLOWED_CATEGORIES`, `ALLOWED_PAYMENT_STATUSES`).
    Arbitrary or malicious object keys sent by attackers are ignored.
  - Layer 3 (Database Schema Enforcement):
    Mongoose schema validates types, regex patterns, minimum values, string bounds, and enum
    sets prior to MongoDB write operations.

10.2 Error Handling Specifications:
  1. Mongoose `ValidationError`:
     Extracted via `Object.values(err.errors).map(e => e.message)` and joined with semicolons,
     returning HTTP 400 Bad Request.
  2. Mongoose `CastError`:
     Triggered when an invalid ID string is supplied to `findOne` or `updateOne`. Caught explicitly
     to return HTTP 400 Bad Request with "Invalid registration ID format".
  3. Non-Existent Resources:
     When an ID is valid but does not match any document, endpoints return HTTP 404 Not Found.
  4. Database Disconnection:
     In `config/db.js`, connection failure triggers an explicit error log and terminates the process
     (`process.exit(1)`), preventing the server from running in a degraded state.

16. DEVELOPMENT HISTORY, REFACTORING LOG & KNOWN ISSUES
================================================================================

16.1 Refactoring & Enhancement Log:
  1. Systematic Identification Enhancement:
     - Initial State: The prototype originally exposed MongoDB's internal 24-character hex `_id`
       directly in table cells.
     - Enhancement: Added `registrationId` field (`EM101`, `EM102`, etc.) with unique B-Tree indexing.
       Implemented auto-increment calculation during `POST /api/registrations`. Updated search-by-ID
       to match `registrationId` case-insensitively.
  2. Express Route Precedence Resolution:
     - Issue: The aggregation route `GET /stats/summary` was initially declared below `GET /:id`.
       Express attempted to cast the string `"summary"` as a 24-character hexadecimal MongoDB ObjectId,
       throwing a Mongoose `CastError`.
     - Fix: Moved `GET /stats/summary` above `GET /:id` in `routes/registrations.js`.
  3. Mongoose Duplicate Index Warning:
     - Issue: `models/Registration.js` declared `registrationId: { type: String, unique: true }` and
       also had `registrationSchema.index({ registrationId: 1 })`, causing duplicate index creation warnings.
     - Fix: Cleaned schema to retain `unique: true` constraint without redundant index declarations.
  4. Quick Academic Demonstration Tooling:
     - Enhancement: Added a "Fill Sample" button to `public/index.html` and `public/js/app.js` with rotating
       sample participant records so that students do not need to manually type 8 fields during viva evaluation.
  5. One-Click Launcher (`run.bat`):
     - Enhancement: Built automated batch launcher. Added a 1.2-second background timer using PowerShell
       before launching the browser to ensure the Express server is fully listening before the browser loads.

16.2 Known Limitations / Out-of-Scope Elements:
  - Authentication: User login and role-based access control (RBAC) are not implemented, as the project
    focuses exclusively on Database Systems concepts (query execution, indexing, operator demonstrations).
  - Multi-Collection Normalization: Events and Participants are unified in a single document collection
    to optimize read throughput and focus on complex query operators.
